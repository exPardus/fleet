### 3.2 Can `launch_home` be influenced? — **NO**

Three things had to hold and all three do.

assignment at `bin/fleet_statusline.py:704` cannot move it, even though it happens *before*

correct — which is the strongest form of the fix and is what the lane claimed.

**Nothing on the resolution path writes `FLEET_HOME`.** By AST, `FLEET_HOME` is rebound in exactly
two functions:

```

```

Neither is reachable from `resolve_blob_home` (which calls `resolution_population`, `resolve_home`,
`lookup_home_for_sid`, `read_registry_at` — all pure or read-only). So the capture at line 698
cannot be pre-empted.

**"Every entry path" has exactly one member, and the default is fail-closed.** Full caller set:

```

bin/fleet_statusline.py:627  def _load_delegates(legacy_home=None)
bin/fleet_statusline.py:634      _read_delegates(fleet.statusline_chain_path())
```

One call site, and it passes `launch_home`. Every other caller — including a future one — gets
`legacy_home=None`, which reads the machine plane **only**. That is the right default: a new caller
that forgets the anchor loses the migration, it does not gain a foreign read.

### 3.4 The new question — is a machine-global chain file the right trust model?

**Yes, and the trade is strictly in the defender's favour.** The honest way to state what changed:

- **Before:** cross-home **execution**. The attacker's whole capability was *"appear in
  `~/.claude/fleet-homes.list` and put a string in your own registry."* Unauthenticated,
  automatic, every ten seconds, invisible.
- **After:** cross-home **configuration**. To reach `subprocess.run(..., shell=True)` an attacker
  must now write `~/.claude/fleet-statusline-chain.json`, which requires code execution as the
  user — and an attacker who has that does not need the chain file, because they can write
  `~/.claude/settings.json` or edit `bin/fleet_statusline.py` directly. This is exactly the
  `ULTRAREVIEW-2026-07-30` argument, and here it applies correctly: *"a finding whose fix does not
  change the outcome of its own failure scenario is not a defect."*

So the answer to *"has cross-home execution been replaced by cross-home configuration"* is: yes,
and configuration by an attacker who already owns the account is not a capability. The delegate is
genuinely a machine-scoped fact — Claude Code allows exactly one `statusLine` entry in exactly one
`~/.claude/settings.json` — so a per-home copy was the anomaly.

**One residual, and it is the install half's, which the lane already filed rather than took.**
`_capture_statusline_delegate` (`bin/fleet.py:5979-5988`) writes the machine file with a bare
`path.write_text(...)`: a full replace, no backup, no refusal, no validation, and now
machine-wide. `_install_statusline` takes a `settings.json` backup two dozen lines later and gives
the chain file none. Every fleet on the box shares one unvalidated `shell=True` sink. See MINOR 3.

`_safe` is reached only by an *unknown* bucket label and by `_reset_clock`'s fallback. Fleet's own
vocabulary bypasses it entirely (`_LABEL[bucket] if bucket in _LABEL else _safe(bucket)`), no

```

   ['attached', 'dead', 'idle', 'idle+mail', 'limited', 'over_budget', 'over_ceiling', 'working']

`[`/`]` in any _SUP_STATE_LABEL value: False

```

### 4.3 What `_safe()` still lets through — **24 CHARS OF FLEET'S OWN VOCABULARY**

The bracket insight closes the *nameplate*. It does not close the *words*, and the words are
fleet's too:

```

status='no live workers'          -> '[fleet]  no live workers 1'
```

`sup held` is the **command-tier** field's vocabulary and `no live workers` is the all-dead

the forgery always carries a trailing count, always sits after the real tier and bucket fields

### 4.5 The pin — **REAL**, and the `\x1b[1;31m` plant fires

```

attacker SGR \x1b[2K                                   -> FIRES: control chars [(9, '\x1b')]
```

The palette-by-value check does what the lane says: a shape-matching regex would have waved

### 4.6 The old ASCII pin's comment — **TRUE**

```

'\x1b[1;31m' .isascii() = True

'\x9b2K'     .isascii() = False
```

The comment names ESC as the blind spot and ESC is genuinely `.isascii() == True`. The last row is
worth knowing and does not contradict it: the old pin *does* catch a C1 CSI, so the two pins
overlap on C1 and diverge on C0 — which is why keeping both is right.

## 9. THE MINORS

### MINOR 1 — the pin's declared bound is not a bound the code meets

`assert_no_terminal_control(line, limit=200)` asserts a bounded length, and the attacker-maximised
line is **287** (§4.4, driven end to end from a real registry). The only shipped test that reaches
the `+N unknown` field builds 500 workers of **one** bucket shape, so the line stays short and the
limit is never approached:

```python
snap = {"ok": True, "workers": [
    {"status": f"{'Z' * 300}-{i}", ...} for i in range(500)], "totals": {}}
line = sl.render_statusline(snap, color=False)
assert_no_terminal_control(line)
```

Nothing is broken today; the finding is that `200` is a number nobody measured against the real
worst case, and the next person who tightens `_FIELD_LIMIT` or `_MAX_UNKNOWN_BUCKETS` will trust
it. Either raise the constant to the measured bound with the derivation written down, or add a
fixture that combines all eight known buckets + age suffixes + a hostile reset clock + three capped
unknowns.

### MINOR 2 — the new palette pin never sees the field the discharge added (mutant X4)

Painting `+N unknown` with a hard-coded non-palette `\x1b[31;1m` **survives the whole target
suite**. The mechanism: `assert_no_terminal_control` is the only pin that would catch a
non-palette SGR, and the only test that renders `+N unknown` calls
`render_statusline(snap, color=False)` — so `paint()` returns the text unpainted and the escape
never exists. The hostile-status tests do parametrize `color=[True, False]`, but they build one
worker and never produce the overflow counter.

Not attacker-reachable (`_safe` stops foreign SGR), so this is fleet's-own-code coverage, and it is
precisely the "survivors cluster on what the author added last" prediction landing. One
`color=True` case over the overflow counter closes it.

### MINOR 3 — the machine-plane chain file is an unvalidated machine-wide `shell=True` sink

`_capture_statusline_delegate` (`bin/fleet.py:5985-5988`) writes it with a bare `write_text`: full
replace, no backup, no refusal, no schema check — while `_install_statusline` takes a timestamped
backup of `settings.json` twenty lines later. Moving the file to the machine plane was right (§3.4)
and it also widened this file's blast radius from one home to every fleet on the box. Not an
escalation — writing it requires code execution as the user — but the asymmetry with the
`settings.json` handling right beside it is worth one `elif`. **This is the install half the lane
explicitly filed rather than took** (`w50/launchfix`'s function this wave), and I file it the same
way.

### MINOR 4 — the digest is checkout-relative, and it is **already in `BRIEF-TEMPLATE.md`**

Filed against §18 while I worked; **it landed on `main` mid-gate** as `c6ddf0f`
(`docs/lanes/BRIEF-TEMPLATE.md`, +63 lines, *"Proving a run changed nothing — NOT with
`git write-tree`"*), verbatim and **without this caveat**. So this is no longer a note on one lane
report — it is live in the campaign's canonical template, which every future brief inherits.

The instrument is right and the vacuity finding it replaces is real. The gap is one sentence.
Two **clean** worktrees of the **same commit** `5a47819` on this machine:


Same file count, different digest. Cause, measured:

```

  docs/lanes/w50-d.md:            A=82690B B=81346B  A_crlf=1344 B_crlf=0
  tests/test_statusline_home.py:  A=61015B B=59816B  A_crlf=1199 B_crlf=0
```

`core.autocrlf=true` and every blob is LF, so a file **checked out** gets CRLF while a file
**authored in place** keeps LF — and `git status` calls both clean. `files=242` does not catch it,
by design.

The template's stated use — *"print it immediately before the floor run and immediately after; the
two lines must match, `files=` included"* — is **sound and unaffected**; that pair is within one

checkout-relative — `core.autocrlf` means a file's working bytes depend on whether it was written
in place or checked out, and `git status` calls both clean. Only the before/after PAIR is
meaningful; never compare a digest across worktrees or machines, and never quote one as a tree
identity."* Note the irony worth recording: this is the same class as the finding the template
amendment exists to fix — an instrument trusted past the claim it can actually make.
