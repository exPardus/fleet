## 4. `words, exit 0`, AND THE REFUSAL CLAUSE — WHERE I DIVERGE, DELIBERATELY

The brief asked me either to defend the position that the refusal clause does not apply to a view,
or to implement it. **I take a third position, and it is narrower than either.**

§5 step 5 splits the surface exactly once: *"mutating verbs refuse with the named remedy, and views
render `[fleet]: no home` and exit 0"*. The statusline is unambiguously on the view side, so it has
no refusal and prints **no remedy** — no `--fleet-home`, no `FLEET_HOME`, no "run `fleet homes`".
That much is the spec's own split, not my invention, and it is why the terminus prints
`fleet.NO_HOME_LINE` and stops.

But **`ambiguous` is not the terminus**, and it is the one state where a view has something the
operator genuinely cannot get anywhere else: this session is claimed by more than one fleet. §5's
refusal contract is *"facts + the `fleet homes` view, never a paste-ready command with a chosen
home"*. On this surface:

- **The `fleet homes` view is not available.** It is multi-line by construction; the statusline is
  one line under the input box, refired after every assistant message. Rendering it there is not a
  stylistic objection — it would repaint the operator's terminal every few seconds.
- **So the honest one-line residue of "facts, and no chosen home" is the COUNT.**
  `[fleet]: home ambiguous (2)` states how many homes claim this session and leaves every one of
  them unnamed. Naming one would be choosing — the exact failure mode the clause exists to
  prevent. Naming all of them would be the paragraph the surface cannot carry.
- The full view is one `fleet homes` away, and every verb-tier surface already embeds it
  (`_refuse_ambiguous_lookup`, `_terminus_refusal`, `apply_resolved_home`'s disagreement arm).

`test_the_ambiguity_word_names_no_home_and_pastes_no_command` pins the negative: the line contains
none of `--fleet-home`, `FLEET_HOME`, either home path in either spelling, or `fleet homes`. Mutant
**M5** appends `-- name one with --fleet-home` and dies on it.

**I did not silently drop the clause. I implemented the half a one-line surface can carry and named
the half it cannot.** If the operator rules that an ambiguous statusline should say nothing at all,
that is a one-line change to `render_home_terminus` and one test.

The other three contract points are unmoved and now **driven rather than inherited** (§5's
`TestTheResolutionPathIsAView`):

- **no lock, no write, no mkdir, no subprocess** across all five resolution shapes (single / hit /

## 5. THE CHAIN FILE — THE QUESTION THE BRIEF COULD NOT ANSWER

**The facts, all MEASURED.**

1. `statusline_chain_path()` is `state_dir() / "statusline-chain.json"`, i.e. `FLEET_HOME`-relative;
   `fleet_statusline._chain_path()` computes the same path at call time.
2. The live home holds one:
   `C:/proga/claude-fleet/state/statusline-chain.json` → a delegate command pointing at
   `C:\Users\Techn\.claude\plugins\cache\caveman\…\caveman-statusline.ps1`, `captured_at
   2026-07-09T16:38:33Z`. My worktree holds none.
3. `_install_statusline` decides what to chain with
   `foreign = bool(incumbent) and "fleet_statusline.py" not in incumbent`.

**The answer: the chain file is INCOHERENT with home resolution, and the incoherence is a
plane error, not a path error.**

The delegate is a **machine-scoped** fact. Claude Code allows exactly one `statusLine` entry, in
one `~/.claude/settings.json`; the delegate is *whatever was in that one entry before fleet
replaced it*. It has nothing to do with which fleet a session belongs to. Storing it under a home
means:

- **Before slice (d)** the split is already visible: whichever home `$FLEET_HOME` names decides
  whether the operator's own statusline row appears. My worktree has no chain file, so a session
  resolving there loses the `[CAVEMAN]` row entirely — MEASURED above, the third live run prints
  `[fleet]: not initialized` and no delegate row.
- **After slice (d)** it becomes *per session*: the chain follows the resolved home, so the
  operator's own statusline appears for sessions belonging to home A and vanishes for sessions
  belonging to home B. Same terminal, same operator, different rows depending on which fleet the
  session is in. That is incoherent on its face.
- **And `init --statusline --chain` cannot repair it on the second install**, by construction: home
  B's install sees home A's fleet statusline command as the incumbent, judges it **not foreign**
  (it contains `fleet_statusline.py`), captures nothing, and overwrites the machine-global entry
  with B's script path. The operator's original delegate now exists only in A's chain file. The
  `foreign` test is *correct* for its own purpose — chaining a fleet statusline would make it
  invoke itself once per refresh forever — and wrong for this one.

**What slice (d) does about it: one thing, and deliberately only one.** It resolves the home
**before** running the delegates, so a single render reads its delegate and its roster from **the
same home**. Resolving afterwards would have read the delegate out of one home and the roster out
of another — a split-brain line. `test_the_chain_is_read_from_the_home_the_blob_sid_resolved` pins
it; mutant **M4** pins the chain path back to the install and dies.

**What it does NOT do, and why.** It does not add a fallback ("read the resolved home's chain, else
the install's"). That would invent a precedence rule the spec has not ruled on, inside a view, on
ratified-adjacent ground — and it is a no-op on this machine anyway, where `INSTALL_ROOT` *is* the
live home. Nor does it move the file: `_capture_statusline_delegate` and `statusline_chain_path`
live in `bin/fleet.py`, next to the sibling lane's `_install_statusline`, and the fence says stop
and report rather than edit.

**Recommendation for the docket, two coherent options:**

| option | where the chain lives | argument |
|---|---|---|
| **(i) machine plane** — `~/.claude/fleet-statusline-chain.json` | next to the settings file it was captured from | one `statusLine` per machine ⇒ one chain per machine. ## 12. BLOCKING 2 — WHAT A FOREIGN HOME MAY PUT ON THE OPERATOR'S SCREEN

### 12.1 The sanitiser

One function, `_safe(text, limit=24)`, on every registry-derived field:

- **bounded at 24 characters**, `~` marking the cut, so a 400-character status cannot push the
  operator's own rows off the screen;
- **brackets neutralised** (`[`→`(`, `]`→`)`).

*overwriting* fleet's row — but the line still renders a **second nameplate** mid-line, and an

blacklist: brackets are the nameplate's SYNTAX on this surface and no status word needs them, so
foreign text does not get to speak in it. `test_no_foreign_status_can_render_the_nameplate` drives
four forgeries and asserts `line.count("[fleet]") == 1` and that no `[` survives past the head.

## 18. THE WORKING-TREE DIGEST — WRITTEN TO BE COPIED INTO `BRIEF-TEMPLATE.md`

The manager asked for the replacement instrument stated precisely enough for a stranger to follow,
because this text is going into the template. Here it is, self-contained.

**The defect.** `git write-tree` hashes the **index**, not the working tree. With unstaged changes
it returns `HEAD^{tree}` unchanged, so a before/after comparison built on it **cannot fail** while
the index is untouched — which is every lane's normal state during a test run. It is also blind to
untracked files. Both halves were reproduced independently by this lane and by its gate; the gate's
receipt is three lines and shows `write-tree == HEAD tree` while a tracked blob differed.

**The replacement.** A sha256 over every file in the working tree, keyed by path:

```python
#!/usr/bin/env python3
"""A digest of the WORKING TREE, not the index. Print before and after a run and
compare; identical means the run modified nothing."""
import hashlib, sys
from pathlib import Path

ROOT = Path(sys.argv[1] if len(sys.argv) > 1 else ".").resolve()
SKIP = {".git", "state", "logs", "mailbox", "__pycache__",
        ".pytest_cache", ".ruff_cache", ".fleet-index"}

h, n = hashlib.sha256(), 0
for p in sorted(ROOT.rglob("*")):
    if any(part in SKIP for part in p.relative_to(ROOT).parts) or not p.is_file():
        continue
    h.update(p.relative_to(ROOT).as_posix().encode("utf-8"))
    h.update(hashlib.sha256(p.read_bytes()).digest())
    n += 1
print(f"{h.hexdigest()}  files={n}  root={ROOT}")
```

**How to use it.** Print it immediately before the floor run and immediately after; the two lines
must match, `files=` included. The `files=` count is not decoration — it is what catches a skip rule
that silently swallowed the tree.

**Why those skips.** `state/`, `logs/` and `mailbox/` are gitignored runtime planes that a run may
legitimately touch; the cache directories churn by design and would drown the signal. Everything
else — including untracked files, which `git write-tree` cannot see at all — is in.

**What it does not replace.** `tests/conftest.py`'s session-scoped
`_the_real_install_plane_is_byte_identical_afterwards` hashes the git-tracked code plane inside the
run and is strictly better *for that plane*, because it fails the suite rather than a human's
eyeball. The digest covers the whole tree and is what a lane reports. Use both.
