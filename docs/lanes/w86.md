and a ranked list of cuts by tokens saved per unit of work, relayed before any cut lands.

## Where the cache_read goes: resume chains, not turns

Grouping sessions by their first recorded timestamp (a session and every file it was later
`--resume`d into share one anchor) finds a small number of **chains**: one growing
conversation, replayed in full on every resume, spread across many session files.

- **home**: 24 chains. ONE chain — 21 resumed session files, growing 706→1,067 turns over
  2026-09-10T15:29Z→2026-09-11T14:15Z (~23h) — carries 5,683,903,210 cache_read tokens:
  **81.4% of the home project's cache_read, 58.1% of the entire host's.**
- **tap**: 10 chains. ONE chain — 2 sessions, up to 1,310 turns — carries 1,025,646,562
  cache_read tokens: 45.3% of tap's, 10.5% of the host's.
- Combined, these **two chains (23 of 91 session files) are 68.6% of every cache_read token
  measured on this host this week.**
- **worker lanes show nothing like this**: the largest worker-side chain is 2 sessions,
  335 turns, 95.6M tokens — two orders of magnitude smaller. Disposable lanes stay disposable;
  the persistent supervisor/interface identity does not.

MEASURED by: grouping `*.jsonl` by (project dir, first `timestamp`), summing `cache_read_input_tokens`
per group. Script: `python3` over `glob("~/.claude/projects/*/*.jsonl")`, no file content printed.

## Ranked cuts (tokens saved per unit of work)

1. **Cap the supervisor/interface resume chain.** 6.71B of 9.79B host cache_read tokens
   (68.6%) sit in two chains, both persistent-identity homes (fleet + tap), neither on the
   worker side. Evidence: chain-grouping above. This is the entire game — nothing else
   measured this round is within 10x of it. Proposed lever (operator's call, not built here):
   relaunch fresh from the journal checkpoint past some turn/token threshold instead of native
   `--resume`, so each new body pays for a compact checkpoint, not the full growing history.
2. **Re-measure everything else only after (1) lands.** With the two dominant chains removed,
   the remaining 3.08B tokens (31.4%) may redistribute in ways this pass can't see — none of
   the other suspects below individually explains a double-digit share.

### Suspects checked and found small (one line each, per the method rule)
- **Idle/trivial turns** (`output_tokens<=80`, host-wide): 430 of 34,316 turns (1.3%), carrying
  125,420,607 cache_read tokens (1.3% of host cache_read). Not a lever at this scale.
- **`skills/fleet/SKILL.md` (14,242 B) / `supervisor/briefs/server-standing.md` (1,938 B)
  reloads**: 1,504 / 1,530 substring occurrences host-wide (ESTIMATED — raw occurrence count,
  not confirmed unique-read count). Even at face value, bytes/4 × occurrences ≈ 5.4M + 0.7M
  tokens ≈ 0.06% of host cache_read. Reloading these files is not where the tokens are.
- **Statusline**: DISPROVED by code, not by transcript — `docs/SPEC.md` §"terminal-surface"
  and this repo's CLAUDE.md doctrine both state views (statusline, `/fleet:*`) are read-only
  and fleet "injects context into no session." The statusline renderer never enters any
  model's context; its cost is zero by construction, not by measurement.
- **Keeper wakes of parked bodies**: only 20 mentions of `parked-not-woken` host-wide this
  week — a low-frequency event. Not sized further this round; worth a per-wake cost if the
  operator still suspects it after (1) lands.

### Not sized this round (occurrence count only, flagged for a follow-up pass)
`checkpoint` mentions: 9,880. `wave-close` mentions: 10,416. `sup-status`/`sup-guard` output:
7,066. `state/journals/` reads: 2,114. `state/interface/` board: 1,048. `fleet brief`: 429.
These are raw substring counts (not per-call byte sizes), so they cannot be ranked against
the resume-chain number honestly — converting them needs per-event output-byte sizing, which
is a second measurement pass, not a guess. None of them can beat 68.6% even at generous
assumptions, so they are ordered here by occurrence only, lowest priority to chase next.

## Method note
Every number above is a script aggregate over `message.usage` fields or `os.path.getsize` /
`re.findall` counts on raw file bytes. No transcript prose, operator text, or file content was
read into this session at any point; scripts are in the job's tmp dir and are reproducible
against the same `~/.claude/projects/` tree.
