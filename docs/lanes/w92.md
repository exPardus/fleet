# w92 — stop landed lanes' sessions inside the same wave-close run

DONE means: `fleet wave-close` stops the session of every lane it marks
`lane_state=landed` through `_stop_native_session_status`, then reaps, so the
lane arm of the reap predicate fires inside the same wave-close run and the
slot is free when the verb returns.

## Root cause and fix
Reap ran before landing was marked, and nothing stopped a just-landed lane's
session, so `_reap_protection`'s live-PID veto (`roster-live`) never cleared
inside one wave-close run. New `_wave_stop_landed_sessions(landed_names, run,
which)` in bin/fleet.py, called from `cmd_wave_close` after push/prune/notify
-- never under `fleet_lock()` (each `claude stop` call can block up to its
timeout). Reads the registry read-only, resolves each landed lane's
`session_id`, calls `_stop_native_session_status`; a non-ok outcome (e.g.
`daemon-transient`) is reported, not dropped. A second `_supervisor_reap`
pass follows; both counts print on the `wave-close: lane_state=landed
recorded for: ...` line. `_reap_protection`/`_reap_eligible` untouched --
REJECTED FIX avoided.

## Verified by experiment, not by reading
Real `claude --bg` session, waited for idle status with a live pid, ran
`claude stop <id>`, re-queried `claude agents --json`: the roster entry
disappears ENTIRELY, not just the pid -- the lane arm's existing
`entry is None and status idle` branch. Not a blocker.
